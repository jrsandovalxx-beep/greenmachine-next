## The rendered `None` defect

**REASONING — Real defect, non-blocking for GMF-002 submission 2.**

The finding is credible and important: absent numeric cells carry `NaN` in the sortable data, the Styler payload carries the intended textual reasons, but the rendered component substitutes `None`; the three reasons therefore survive visually only through their different backgrounds.

I do not agree that this makes GMF-002 fail its governing criterion.

GMF-002 says:

> "absence states visibly distinct from zero — a blank cell that could mean either fails"

It does not say that every absence reason must be printed verbatim inside each grid cell.

On the observed surface:

* absence cells are not blank;
* they do not look like numeric zero;
* zero remains visibly `0 · BBE 6`;
* the three absence states retain distinct visual styling.

So the specific failing condition the plan names does not occur.

I will not strengthen an approved criterion after deployment just because the implementation exposed a better UX standard than the plan originally wrote. That would recreate the same governance problem D-049/D-050 are intended to prevent.

## §7 does not justify retroactively rejecting GMF-002

**REASONING — Important distinction.**

§7 says:

> "Absence is a value — every field distinguishes not applicable, not yet observed and source unavailable."

That distinction still exists in `InputSnapshot` and survives into the handed-off element data/configuration. D-061 specifically made AppTest responsible for proving each absence state's rendering as data, while actual visual legibility was deferred to submission 2.

Submission 2 has now shown that Streamlit's final canvas representation is less semantically useful than the payload.

That is exactly the kind of defect deployed verification is supposed to discover. It does not erase the fact that the approved GMF-002 criterion set a narrower acceptance boundary.

I therefore classify this as a semantic/accessibility product defect, not a GMF-002 acceptance failure.

## Remedy vehicle — GMF-003 is authorized; no plan revision required for the detail-surface route

**REASONING — Scope ruling.**

I agree with the Lead's proposed vehicle, with one important boundary.

D-058 already establishes a selection-driven detail surface. GMF-003 is the next metrics and grading screen, must be built on the GMF-002 grid, and is where the next layer of metric presentation belongs.

Therefore, using the existing selection-driven detail surface during GMF-003 to expose an absent metric's reason in words is within GMF-003's existing content scope. It does not require:

* reopening GMF-002;
* a fourth GMF-002 object;
* a plan revision.

That is a scope ruling, not a prescribed UI implementation.

Conversely, if the chosen remedy instead changes the GMF-002 grid-cell representation itself — for example restructuring metric columns specifically to alter how null cells render — that reopens the already approved GMF-002 surface. I would not authorize that change under GMF-003 merely because GMF-003 happens to build on the grid. That route would require an appropriate plan-level authorization.

So the clean existing vehicle is indeed the detail-content route.
