## V3 blocker — closed

**REASONING — Accepted.**

V3 had two conflicting representations of source health:

1. `SourceRecord.availability`;
2. per-field `SnapshotField` state.

V4 removes the first representation rather than attempting to synchronize it.

`SourceRecord` is now identity and provenance only. Health is expressed at the observation that actually succeeded or failed. That is coherent with the fact that one adapter can successfully answer one requested value while failing another within the same snapshot capture.

More importantly, this is implemented rather than asserted:

* `SourceAvailability` no longer exists in the public contract;
* `SourceRecord` has exactly `source_id`, `kind`, `description`, and `provenance`;
* `SOURCE_UNAVAILABLE` and `NOT_YET_OBSERVED` must carry `source_id`;
* only `NOT_APPLICABLE` may omit it;
* `InputSnapshot` verifies every non-null field `source_id` against its source table.
  That resolves the V3 contradictory-state construction.

The phrase “`NOT_YET_OBSERVED` from a healthy source” can now be read as shorthand for that **particular observation having successfully answered with no accumulated sample**, not as a second table-level health flag.

## Ruling — `ParkVenue.savant_venue_id: int | None`

**REASONING — Accepted.**

I agree with Lead's judgment. I do **not** require this field to become another `SnapshotField`.

The distinction from the rejected V2 `metrics_for() -> None` is material:

* `metrics_for()` represented an observed named window and bare `None` collapsed multiple possible absence meanings;
* `savant_venue_id` is reference/join metadata whose `None` has one fixed structural meaning: this reference venue has no corresponding row in the pinned snapshot.

The reference documentation fixes that meaning, and the tests constrain it to exactly one club—the Athletics.

The **observable consequence** of that missing join—the unavailable park-factor value—is separately represented through the proper three-state contract as `NOT_YET_OBSERVED`.

Wrapping the join key itself would duplicate absence semantics rather than clarify them. Its explicit `"identity"` allow-list classification is therefore acceptable.
